# WebGPU 优势验证：A–G 微基准（含 2×2 归因）

**Mol-Vista 配套微基准｜2026-10-19｜肖松涛｜脚本与数据：`bench/micro/`**

> **结论先行**：2×2 补全后，性能差异的主因是"每帧逐对象 uniform 上传"这一实现——WebGPU 逐对象 36 fps，去掉每帧上传后 121 fps，实例化 165 fps；而 WebGL2 逐对象同样 165 fps，说明 API 与 draw 数都不是主因。在此之上：高 draw 提交 WebGPU 有 6× 优势（E），光栅化无 API 优势（G），compute 有 59–73× 优势（C）。

## 一、要回答的问题与实验设计

上一轮实测只证明了"30 fps 不是 WebGPU 的锅"，但没有回答"WebGPU 到底有没有优势"，也没有把"API"与"实现方式"分开。本轮用独立微基准页、同一 4HHB 数据（4779 原子 / 4576 键）、同一 1002×928 视口、同一相机、每帧重绘，做四类对照 + 两个补充：

- A：2×2 因子实验（逐对象 / 实例化 × WebGPU / WebGL2）；
- B：全场景 id pass / 局部 id pass / compute 拾取；
- C：MD 力计算 compute vs 单线程 JS；
- D：同架构（实例化）WebGPU vs WebGL2 轻负载；
- E：draw-call 压力扫描（2–50k/帧）；
- G：重光栅化 overdraw。

环境：i9-12900H / RTX 3060 Laptop / Chrome 155 headless，真实 GPU；统一 1× MSAA、无 SSAO；空载页 rAF 实测 164 fps（刷新上限）。E/G 另加 `--disable-frame-rate-limit --disable-gpu-vsync` 并固定帧数提交。

## 二、微基准 A：2×2 归因

| 后端 / 提交方式 | 帧率 | p95 帧间隔 | CPU 提交/帧 | 能否触顶 |
| --- | --- | --- | --- | --- |
| WebGPU · 逐对象（每帧写一次 uniform） | 36.3 fps | 30.5 ms | 10.65 ms | 否 |
| WebGPU · 逐对象（uniform 静态，只 setBindGroup+draw） | 120.9 fps | 12.2 ms | 1.91 ms | 接近 |
| WebGL2 · 逐对象（uniformMatrix4fv + draw） | 165 fps | 6.2 ms | 2.04 ms | 是 |
| WebGPU · 实例化（2 次 draw） | 165 fps | 6.2 ms | 0.106 ms | 是 |
| WebGL2 · 实例化（2 次 draw） | 165 fps | 6.2 ms | 0.046 ms | 是 |

- **2×2 的结果与预期不同**：补上"WebGL2 逐对象"这一格后，它仍然打满 165 fps（CPU 2.04 ms），并没有掉到 40 fps。所以"逐对象提交"本身不是性能杀手。
- 真正的分界是"每帧是否重新上传每个对象的 uniform"：WebGPU 逐对象每帧 9362 次 writeBuffer → 10.65 ms/36 fps；把上传去掉、只保留 setBindGroup+draw → 1.91 ms/121 fps；WebGL2 的 uniformMatrix4fv 每次约 0.2 µs，所以逐对象仍 165 fps。
- 归因结论：原型 4HHB 的 30 fps 来自"每帧逐对象 uniform 上传"这一实现（约 8.7 ms 的差值），既不是 WebGPU 本身慢，也不是 draw call 数量多（E：10k 次纯 draw 仅 0.33 ms）。
- 修复优先级：实例化（消除每对象状态）> 动态偏移 UBO/批量 uniform（消除每帧上传）> 单纯减少 draw 数。

## 三、微基准 B：三种拾取实现

| 渲染架构 | 全场景 id pass | 局部 id pass（16×16 scissor） | compute 拾取 |
| --- | --- | --- | --- |
| 实例化（9362 对象） | 3.4 ms | 3.3 ms | 3.1 ms |
| 逐对象（9362 次提交） | 36–41 ms | 36–40 ms | 3.1 ms |

- 实例化后三种拾取都 ≤ 3.5 ms；逐对象架构下局部 scissor 几乎不降，compute 拾取绕开提交，稳定 3.1 ms（约 12×）。

## 四、微基准 C：compute 着色器 vs CPU（MD 力计算）

算法：Lennard-Jones all-pairs 力计算 + 速度积分（GPU WGSL compute 128 线程/组；CPU 同公式单线程 JS）。

| 原子数 | GPU compute ms/步 | CPU 单线程 ms/步 | 加速比 | GPU 步/秒 |
| --- | --- | --- | --- | --- |
| 1079（1AKI） | 0.50 | 10.8 | 21.6× | 约 2000 |
| 2500（6LU7） | 1.00 | 43.7 | 43.7× | 约 1000 |
| 4779（4HHB） | 2.15 | 157 | 73×（另一次 59×） | 约 465 |

## 五、微基准 D：同架构 WebGPU vs WebGL2（轻负载）

| 后端（实例化） | 帧率 | p95 | CPU 提交/帧 |
| --- | --- | --- | --- |
| WebGPU | 165 fps | 6.2 ms | 0.105 ms |
| WebGL2 | 165 fps | 6.2 ms | 0.051 ms |

- 轻负载下两者都触顶，无差异；D 只有 2 次 draw，不能代表高 draw 场景（见 E）。

## 六、微基准 E：draw-call 压力扫描

| 每帧 draw | WebGPU CPU 提交 | WebGL2 CPU 提交 | WebGPU GPU ms | WebGL2 GPU ms |
| --- | --- | --- | --- | --- |
| 2 | 0.01 ms | 0.01 ms | 0.03 | 0.09 |
| 1 000 | 0.06 ms | 0.47 ms | 0.37 | 0.67 |
| 5 000 | 0.15 ms | 0.52 ms | 1.37 | 3.48 |
| 10 000 | 0.33 ms | 2.67 ms | 2.43 | 6.35 |
| 20 000 | 0.88 ms | 4.65 ms | 4.58 | 11.97 |
| 50 000 | 2.53 ms | 15.11 ms | 11.69 | 30.55 |

- 分叉点清晰：≤1k draw 两者 <0.5 ms；10k 起 WebGPU 低 6–8×；50k 时每帧总耗时 12.2 vs 31.0 ms。
- 对原型：E 的 10k 次纯 draw 仅 0.33 ms，而 A 的 9362 次逐对象要 10.65 ms——差在每对象 uniform 上传，不在 draw。

## 七、微基准 G：重光栅化（overdraw）

| overdraw | WebGPU GPU/帧 | WebGL2 GPU/帧 |
| --- | --- | --- |
| 32× | 0.66–0.85 ms | 0.60–0.67 ms |
| 128×（约 1.19 亿片元） | 3.0–3.4 ms | 2.3–3.0 ms |

- 高 overdraw 两者 3 ms 量级、差距 <25%，WebGL2 略快：光栅化没有 WebGPU 优势。

## 八、结论：归因与优势边界

- **归因（2×2）**：实例化时 WebGPU/WebGL2 都 165 fps（API 主效应不显著）；逐对象时 WebGPU 36 fps、WebGL2 165 fps，差异来自 WebGPU 每帧 9362 次 writeBuffer（约 8.7 ms），去掉上传后 WebGPU 回到 121 fps。慢是"每帧逐对象上传"这一实现问题。
- **有优势（提交）**：高 draw 数（10k–50k/帧）WebGPU CPU 提交低 6–8×。
- **无优势（光栅化）**：128× overdraw 两者 3 ms 量级、差距 <25%。
- **有优势（计算）**：compute MD 59–73× 于单线程 JS。
- **对开题**：技术路线写成"实例化渲染 + compute 实时 MD"；验收用 2×2 + E 式扫描；PyMOL 只作定性参考，不作为归因证据。
